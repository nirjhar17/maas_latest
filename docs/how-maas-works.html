What Problem It Is Solving

When a platform team wants to expose LLMs to many internal users or teams, the raw model endpoint — a vLLM pod inside Kubernetes — is not enough. It has no authentication, no rate limiting, no per-user quotas, no API-key lifecycle management, and no billing hooks. Every consumer would have unrestricted access and could saturate the GPU in seconds.

Models-as-a-Service (MaaS) is the "front door" layer that sits between your users and your models. It turns the raw inference endpoint into a governed API: users get sk-oai-* API keys, each key is bound to a subscription that carries rate limits, access to specific models is controlled by auth policies, and all of this is enforced before a single token reaches the GPU.

In one sentence: MaaS is an API-key and subscription management plane that enforces auth and quotas at the Gateway edge, so your LLM pods only see requests that have already been authenticated and rate-checked.

The inference engine itself (vLLM via the llm-d stack) is separate. MaaS does not care how inference works internally; it only cares that the request is authorised and within budget before it arrives.

The Stack at a Glance

The full stack has four layers, each with a clear responsibility boundary.

LayerComponentsWhat it does
Entry / GatewayOpenShift Ingress Operator, istiod, Envoy (istio-proxy), Gateway APIAccepts TLS connections, terminates the router cert, routes to the correct backend via HTTPRoutes
PolicyKuadrant (RHCL), Authorino, Limitador, WASM pluginValidates API keys, checks subscription access, enforces token-rate limits — all in the Envoy filter chain before the request moves on
Token Managementmaas-api, PostgreSQLMints, validates, and revokes sk-oai-* keys; stores hashed keys + subscription bindings in Postgres
InferenceLLMInferenceService, vLLM / llm-d-inference-simActually runs the model; receives only pre-authorised requests

Two additional layers support the stack without being in the request path: cert-manager (TLS lifecycle) and Leader Worker Set (coordinates multi-replica inference workloads). The OpenShift service-ca operator is used instead of cert-manager for the Gateway-to-Authorino TLS hop.

Component Map

OpenShift Ingress Operator

Manages the HAProxy-based default router (*.apps Routes) and the openshift-ingress namespace. MaaS does not use HAProxy for serving; instead, the MaaS Gateway lives in openshift-ingress as a separate LoadBalancer Service managed by Istio. On non-cloud clusters a passthrough Route through HAProxy bridges external traffic to the Gateway's MetalLB IP.

GatewayClass: openshift-default

The Gateway API GatewayClass tells OpenShift which controller manages Gateways with this class. The controller is openshift.io/gateway-controller/v1 — this is the OpenShift-native Istio-based Gateway controller, not HAProxy and not the Envoy Gateway project. When a Gateway resource referencing this class is created, the controller provisions an Envoy (istio-proxy) Deployment and a matching LoadBalancer Service.

Gateway: maas-default-gateway

The actual entry point. Lives in openshift-ingress. Has two listeners: HTTP on port 80 (redirect) and HTTPS on port 443 (TLS terminate with the cluster router cert). HTTPRoutes in namespaces labelled maas.opendatahub.io/gateway-access=true attach to this Gateway. The annotation opendatahub.io/managed=false tells OpenDataHub not to take ownership.

istiod / Envoy (istio-proxy)

istiod is the Istio control plane bundled with RHOAI. It programs the Envoy sidecar proxies and the Gateway's Envoy proxy. The Gateway pod is literally an istio-proxy container. Kuadrant's WASM plugin is loaded into this Envoy at startup, which is why the default 1Gi memory limit is insufficient.

Kuadrant (RHCL)

Red Hat Connectivity Link. The umbrella operator that installs and wires together Authorino and Limitador. The Kuadrant CR triggers this reconciliation. Kuadrant exposes higher-level policy CRDs (MaaSAuthPolicy, MaaSSubscription) that translate into Authorino and Limitador rules. The policy layer is attached to the Gateway via targetRef pointing at the Gateway or HTTPRoutes.

Authorino

The authentication and authorisation component within Kuadrant. Runs as a gRPC server in kuadrant-system. The Gateway's Envoy calls Authorino over TLS for every request, passing the Authorization: Bearer <key> header. Authorino calls maas-api's /internal/v1/api-keys/validate endpoint to resolve the key to a user identity and subscription.

Limitador

The rate-limiting component. Also runs in kuadrant-system. After Authorino succeeds, Envoy checks Limitador against the token-rate limits defined in MaaSSubscription. Limitador uses in-memory counters (or Redis in production) and replies with allow or deny. A 429 Too Many Requests response is sent to the client if limits are exceeded.

WASM Plugin

A WebAssembly module loaded by Kuadrant into the Gateway's Envoy proxy at startup. It is the glue that intercepts the request inside Envoy and calls out to Authorino and Limitador as external filter services. This is why deploying the first model triggers a Gateway pod restart — Envoy reloads the WASM module. It is also why the pod needs 2 Gi of memory.

cert-manager vs service-ca

Two separate TLS issuers are at work. The OpenShift service-ca operator generates the authorino-server-cert TLS secret by annotating the Authorino Service with service.beta.openshift.io/serving-cert-secret-name. cert-manager is installed but is used for other purposes (e.g., serving certs on the model endpoints or external ingress). Do not substitute one for the other in the Authorino bootstrap step.

maas-api

A REST API deployed in redhat-ods-applications by the RHOAI operator when modelsAsService: Managed is set in the DSC. It handles key creation, validation, revocation, and subscription resolution. Authorino calls it on every inference request to validate the sk-oai-* key. It reads/writes to PostgreSQL.

PostgreSQL

A plain Deployment (not CloudNativePG) running PostgreSQL 16 in redhat-ods-applications. Connection uses sslmode=disable — plain TCP within the cluster. Stores hashed API keys, subscription bindings, and expiry metadata. The maas-api is the only consumer.

DSCI and DSC

DSCInitialization (DSCI) is a cluster-scoped resource that sets global RHOAI config: the applications namespace, monitoring mode (Managed), and CA bundle trust. DataScienceCluster (DSC) enables individual components. Setting kserve.serving.managementState: Managed and modelsAsService: {managementState: Managed} in the DSC is what triggers the RHOAI operator to deploy maas-api and maas-controller.

LLMInferenceService

A CRD introduced by the MaaS/llm-d stack. Similar to KServe's InferenceService but extended with MaaS-specific fields. Each model gets one LLMInferenceService in the llm namespace. The RHOAI operator reconciles it into a Deployment backed by vLLM (or the simulator container) and creates the corresponding HTTPRoute on the Gateway.

Leader Worker Set (LWS)

An operator that coordinates multi-pod workloads where all pods must start together (leader + workers). Used for distributed inference across multiple GPUs or nodes. Not exercised by the single-GPU models in this guide but is installed as a prerequisite because the LLMInferenceService CRD depends on it.

Request Flow: Step by Step

Here is the journey of a single inference request from a client laptop to the model and back. The same path applies whether the model is the simulator or a real GPU-backed vLLM pod.

(HAProxy, non-cloud only) participant GW as Gateway maas-default-gateway
(Envoy / istio-proxy) participant WASM as WASM Plugin
(in Envoy filter chain) participant Authorino participant MaaSAPI as maas-api
/internal/v1/api-keys/validate participant Postgres participant Limitador participant HTTPRoute participant LLM as LLMInferenceService
(vLLM / simulator) Client->>Router: HTTPS POST /v1/chat/completions
Authorization: Bearer sk-oai-... Note over Router: Non-cloud only.
Cloud clients hit GW directly. Router->>GW: TLS passthrough (port 443) GW->>GW: Terminate TLS with router-certs-default
Match HTTPRoute listener GW->>WASM: Invoke Kuadrant ext-authz filter WASM->>Authorino: gRPC CheckRequest (over TLS, authorino-server-cert) Authorino->>MaaSAPI: POST /internal/v1/api-keys/validate {key} MaaSAPI->>Postgres: SELECT WHERE key_hash = SHA256(sk-oai-...) Postgres-->>MaaSAPI: {userId, groups, subscriptionName, expiry} MaaSAPI-->>Authorino: 200 {valid: true, userId, subscriptionName} Authorino->>MaaSAPI: POST /internal/v1/subscriptions/select {subscriptionName, userId} MaaSAPI-->>Authorino: 200 {selected subscription, rate-limit headers} Authorino-->>WASM: OK + metadata (userId, subscription, limits) WASM->>Limitador: RateLimit check (tokens/min for subscription) Limitador-->>WASM: ALLOWED WASM-->>GW: Auth passed, add upstream headers GW->>HTTPRoute: Route to backend by model path HTTPRoute->>LLM: Forward request (with identity headers injected) LLM-->>Client: 200 {"choices": [...]} Note over Authorino,WASM: If key missing/expired → 401 Note over Authorino,WASM: If subscription mismatch → 403 Note over WASM,Limitador: If quota exceeded → 429

A few things to note about this flow. First, Authorino does not cache the key lookup between requests in the default configuration — it calls maas-api on every single request. This is intentional: it ensures that revoked keys stop working immediately without any cache TTL delay.

Second, the rate-limit check by Limitador happens after Authorino has already validated the key. This ordering matters: you only count quota for requests that are genuinely authenticated. An attacker spamming invalid keys does not consume your quota budget.

Third, on cloud clusters (AWS, Azure, GCP) the OpenShift router is not in the path at all. The Gateway's LoadBalancer Service gets a cloud ELB/ALB IP, and the client connects directly. On baremetal or OpenStack, MetalLB assigns an IP, but it is only routable within the cluster network; an HAProxy passthrough Route bridges the external DNS to the MetalLB IP.

How Authorino TLS Gets Bootstrapped

There are two distinct TLS hops in the stack, and they use different certificate sources. It is worth understanding both because misconfiguring either one causes the Gateway to fail auth checks.

The first hop is from the client to the Gateway. The Gateway listener terminates TLS using the cluster's default router certificate, which is stored in the secret named by CERT_NAME (usually router-certs-default) in openshift-ingress. This is the same certificate that *.apps.<cluster> Routes use, so the client trusts it via the cluster's standard CA chain.

The second hop is from the Gateway's Envoy proxy to Authorino. Envoy needs to call Authorino's gRPC port over TLS because the call carries authentication data and flows over the cluster network. A different certificate is needed here: authorino-server-cert in kuadrant-system. This certificate is issued by OpenShift's internal service-ca operator, not by cert-manager, and not by an external CA.

The bootstrap sequence for this second hop is shown below. Understanding the sequence explains why the steps in Phase 2 must happen in a specific order.

The annotation on the Gateway (security.opendatahub.io/authorino-tls-bootstrap=true) signals the MaaS controller to wire the Gateway's Envoy to use the service-ca trust bundle when verifying Authorino's certificate. Without this annotation, Envoy falls back to the system trust store and rejects the service-ca-issued cert, causing every auth call to return a 500 upstream error.

One common trap: if you apply the Kuadrant CR before annotating the Authorino Service, the authorino-server-cert Secret may not exist yet when Kuadrant creates the Authorino deployment. The TLS listener will start without a cert and silently fall back to plaintext. Always apply the service annotation before the Kuadrant CR.

Gateway Deep Dive

The Gateway resource is deceptively simple-looking — it is about 30 lines of YAML. But several of its fields have non-obvious behaviour that is important to get right.

opendatahub.io/managed: false

OpenDataHub's operator continuously reconciles resources it "owns." If the Gateway did not carry this annotation, the ODH operator would periodically overwrite your Gateway spec to match its own desired state, including resetting the parametersRef that sets the 2 Gi memory limit. The managed: false annotation tells ODH: "I created this; leave it alone." This is the same pattern used for other resources you want to manage yourself outside the ODH lifecycle.

parametersRef → ConfigMap maas-gateway-options

The Gateway API spec has no first-class field for setting resource requests on the generated Envoy Deployment. The Istio Gateway controller supports an extension mechanism: if spec.infrastructure.parametersRef points to a ConfigMap in the same namespace, the controller merges the ConfigMap's deployment key (parsed as a partial Deployment spec) into the generated Deployment. This is how the 2Gi memory limit gets set and, critically, how it survives Istio reconciliation. A direct oc patch deployment on the Gateway's backing Deployment would be overwritten on the next reconcile cycle.

Namespace selector: maas.opendatahub.io/gateway-access=true

The Gateway's listeners use allowedRoutes.namespaces.from: Selector with a label selector. Any HTTPRoute in a namespace that lacks this label will be silently rejected by the Gateway controller — the route will show a NotAllowedByListeners status condition and the model will return a 404. Remember to label every namespace that deploys models, including the llm namespace and the redhat-ods-applications namespace where the maas-api route lives.

Two TLS listeners, one cert

The Gateway defines an HTTP listener on port 80 and an HTTPS listener on port 443. The HTTPS listener references the router cert secret (${CERT_NAME}). The HTTP listener exists to handle redirects but does not serve inference traffic. Both listeners restrict allowed routes to the namespace selector above.

Kuadrant, Authorino, Limitador, and WASM

Kuadrant is the name of the upstream project; Red Hat Connectivity Link (RHCL) is its product name in the Red Hat ecosystem. When you install the rhcl-operator, you get the Kuadrant operator. When you apply the Kuadrant CR, the operator bootstraps Authorino and Limitador in kuadrant-system.

The important conceptual point is that Authorino and Limitador do not run "in front of" the Gateway in a traditional proxy-chain sense. They run alongside the Gateway's Envoy, as external services called by the WASM plugin embedded in Envoy's filter chain. The WASM plugin is Kuadrant's mechanism for injecting policy into any Envoy-based gateway without modifying Envoy itself.

When a MaaSAuthPolicy is applied, the Kuadrant operator translates it into an Authorino AuthConfig resource. This tells Authorino which requests to intercept and what to do with them. When a MaaSSubscription is applied, it translates into a Limitador RateLimit resource.

The WASM plugin itself is compiled Rust code, deployed as a .wasm binary embedded in the Kuadrant operator image and pushed into Envoy at startup via the WasmPlugin Istio extension. This is what causes the Envoy memory pressure: the WASM module needs to be JIT-compiled in the Envoy process, which takes additional heap. The first model deployment triggers this load if Kuadrant has not already programmed the plugin.

Subscription tiers and the targetRef pattern

Each MaaSSubscription has a targetRef pointing at the Gateway. This is the Kuadrant policy attachment model, borrowed from the Gateway API Policy Attachment spec. The subscription lives in the models-as-a-service namespace and attaches to the Gateway in openshift-ingress by name. Similarly, the MaaSAuthPolicy attaches to the Gateway and tells Authorino which AuthConfig to apply for that Gateway's routes.

The two built-in tiers for each model are free (100 tokens/min, priority 10) and premium (100,000 tokens/min, priority 20). Higher priority wins when a key is bound to multiple subscriptions. These values are intentionally low for lab defaults — production deployments should adjust them in the MaaSSubscription YAML before applying.

PostgreSQL and the Two Secrets

The PostgreSQL setup is deliberately simple: a plain Deployment (not CNPG, not an Operator-managed cluster) running a single replica of the RHEL-9-based PostgreSQL 16 image, backed by a 20 Gi PVC. The design decision is that MaaS needs a reliable datastore for key metadata, not a highly-available production database; the RHOAI operator manages the deployment lifecycle.

There are exactly two secrets, and confusing them is a common source of crashes:

  • postgres-creds — consumed by the PostgreSQL pod itself via environment variables (POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB). This secret tells the PostgreSQL process what user and database to create on first boot.
  • maas-db-config — consumed by the maas-api pod via a single environment variable (DB_CONNECTION_URL). The URL contains the same password and uses sslmode=disable because the connection is pod-to-pod within the same namespace.

Both secrets must exist in the redhat-ods-applications namespace before the DataScienceCluster is applied. If maas-api starts before maas-db-config exists, the pod enters CrashLoopBackOff and you must delete the pod to trigger a fresh start after the secret is created.

Both secrets are created imperatively with oc create secret generic and should never be committed to git. The connection URL uses a randomly generated password produced at deploy time with openssl rand.

RHOAI CRDs: DSCI, DSC, and MaaS Objects

The RHOAI operator has a two-tier configuration model. The DSCInitialization (DSCI) is applied first and sets cluster-wide concerns: which namespace to use for applications (redhat-ods-applications), whether the operator should manage the monitoring stack, and what trusted CA bundles to inject. There is only one DSCI per cluster.

The DataScienceCluster (DSC) comes second and controls which components are enabled. The key fields for MaaS are:

spec:
  components:
    kserve:
      serving:
        managementState: Managed   # enable model serving
      modelsAsService:
        managementState: Managed   # enable MaaS — deploys maas-api + maas-controller

Once the DSC is applied with these settings, the RHOAI operator creates the models-as-a-service namespace, deploys maas-api and maas-controller in redhat-ods-applications, installs the MaaS CRDs, and creates the default-tenant CR. This is why Phase 3 (PostgreSQL) must come before Phase 4 (DSC): maas-api will crash immediately if it cannot connect to the database.

MaaSModelRef

After an LLMInferenceService is deployed, a MaaSModelRef in the same namespace registers it with the MaaS control plane. The maas-api reads all MaaSModelRef objects across namespaces to build its model catalogue. When a client calls GET /v1/models, the response comes from this catalogue.

MaaSAuthPolicy and MaaSSubscription

Both live in the models-as-a-service namespace. MaaSAuthPolicy defines who can access the model — in the default manifests it allows system:authenticated, meaning any user with a valid OpenShift identity. MaaSSubscription defines the rate limit tiers and binds them to the Gateway. Together they are what Authorino and Limitador use to make per-request decisions.

Model Serving: Simulator vs GPU

The simulator uses a CPU-only container (llm-d-inference-sim) that accepts inference requests and returns random plausible-looking completions. It does not actually run a language model. This makes it ideal for validating the entire auth/gateway/quota stack without any GPU infrastructure. The startup time is about 30 seconds.

GPU models use the Red Hat AI Inference Server (RHAIIS), which is a productised build of vLLM. Each model is packaged as an OCI "modelcar" image from registry.redhat.io — a container that contains only the model weights and is used as an init container to copy weights into a shared volume before the vLLM serving container starts. This approach avoids HuggingFace downloads in production deployments.

GPU sizing guidance:

  • Simulator: no GPU; 100m–500m CPU, 256–512 Mi memory
  • Granite 4.0-h-tiny FP8: ~8 GB VRAM; any NVIDIA GPU
  • Gemma 2 9B IT FP8: ~12 GB VRAM; single A10G (24 GB VRAM recommended)
  • GPT-oss-20b: ~16 GB VRAM; A10G or L40S (AWS g6e.2xlarge has an L40S)

The simulator uses hf://sshleifer/tiny-gpt2 as its model URI, which can trigger HuggingFace's Xet protocol and cause the storage-initializer init container to hang. If the model pod is stuck in Init:0/1 for more than 5 minutes, patch the environment variable HF_HUB_DISABLE_XET=1 onto the Deployment to fall back to standard HTTP downloads.

Field Gotchas

These are the configuration details that are not obvious from reading the CRD specs and that have caused real deployment failures.

opendatahub.io/managed: false (Gateway annotation)

Without this annotation, the ODH operator periodically reconciles the Gateway and overwrites your custom spec, including the parametersRef that sets the 2 Gi memory limit. Always set this annotation when creating a Gateway you manage yourself.

parametersRef in Gateway spec, not in Deployment

The 2 Gi memory limit cannot be set by patching the Envoy Deployment directly because Istio's reconciler overwrites it. It must be set via spec.infrastructure.parametersRef in the Gateway resource pointing at a ConfigMap. The ConfigMap must be in the openshift-ingress namespace and contain the deployment key with a partial Deployment spec. This is an Istio-specific extension to the Gateway API, not part of the Gateway API standard.

Namespace label: maas.opendatahub.io/gateway-access=true

Every namespace that creates HTTPRoutes attached to the MaaS Gateway must have this label. The Gateway controller enforces this via the allowedRoutes.namespaces.selector. Missing this label on the llm namespace is the most common reason a freshly deployed model returns 404 from the Gateway.

Apply Kuadrant pieces separately, not with oc apply -k

The Kuadrant operator auto-creates an Authorino CR when it reconciles the Kuadrant resource. If you apply the full kuadrant/ kustomization in one shot, your Authorino CR may conflict with the auto-created one, or the TLS patch may arrive before Kuadrant has finished creating the Authorino deployment. Always apply namespace.yaml, service-annotation.yaml, kuadrant.yaml separately, wait for Kuadrant ready, then patch Authorino.

Two DSCI apply stages

The OdhDashboardConfig CRD does not exist until after the RHOAI operator has reconciled the DSC and installed the CRD. Applying the full 04-rhoai-config/ kustomization in one shot will fail on the first run because OdhDashboardConfig is unknown. Apply DSCI first, wait for ready, apply DSC, wait for ready, then apply the dashboard config.

sslmode=disable in maas-db-config

The PostgreSQL deployment is a simple Deployment without TLS configured on the server side. The connection URL in maas-db-config must include sslmode=disable. If you use a CNPG-managed PostgreSQL cluster (as in James's scratch notes), it will have TLS enabled and the connection URL must change accordingly.

What Is Optional

The following capabilities are mentioned in various contexts around MaaS but are not required for the core deployment described in this repository.

Observability (Phase 7) Optional

Phase 7 of the lab guide adds the Cluster Observability Operator (COO), OpenTelemetry, and Tempo for full distributed tracing and metrics dashboards in the RHOAI UI. The core MaaS functionality works without any of this. User Workload Monitoring (enabled in Phase 2) is needed if you want the observabilityDashboard feature flag in the dashboard, but the inference API and auth enforcement work whether or not UWM is configured.

CNPG TLS, custom CA, proxy user-ca-bundle Optional

James's from-scratch notes describe an alternative approach using CloudNativePG for the PostgreSQL cluster (with TLS), a custom CA injected via the proxy user-ca-bundle mechanism, and pinning the RHCL operator version to 1.3.4. These are valid production hardening steps but are not required for the standard connected lab deployment covered here. If you follow this path, the DB_CONNECTION_URL in maas-db-config needs TLS parameters, and you must add the custom CA to the DSCI trusted bundle.

COO installed early Optional

James's notes also mention installing the Cluster Observability Operator in Phase 1 rather than Phase 7. This is safe — installing COO early does not affect any other component — but it adds operator CSV wait time in Phase 1 for no immediate benefit unless you are also configuring observability in Phase 7.

External Models Optional

The ExternalModel CRD allows MaaS to proxy requests to third-party APIs (Anthropic Claude, OpenAI, Gemini). External models are registered with an ExternalModel CR instead of an LLMInferenceService and appear in the same model catalogue. This feature is covered in the lab's Phase 8 and requires API keys for the external provider to be stored as Secrets.

MetalLB Optional

On AWS, Azure, GCP, or any cloud platform where oc get infrastructure cluster -o jsonpath='{.status.platform}' returns a cloud name, the LoadBalancer Service for the Gateway automatically gets an external IP from the cloud provider. MetalLB is only needed on baremetal, OpenStack, RHPDS, or SNO clusters where no cloud load-balancer controller exists.

GPU Operators Optional

Node Feature Discovery and the NVIDIA GPU Operator are only needed if you plan to run real GPU models (granite-tiny-gpu, gemma, gpt-oss-20b). The simulator runs entirely on CPU and does not need any GPU infrastructure. Install the GPU operators only after the core MaaS stack is verified to be working.

For the deploy steps that correspond to this architecture, see the README. For official product documentation, see the RHOAI 3.4 MaaS Docs.
